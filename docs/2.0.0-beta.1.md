# AffixIO 2.0.0-beta.1 Guide (historical)

This guide was written for the 2.0.0-beta.1 candidate. Its capabilities, boundaries and lifecycle notes still describe the released 2.0.x workflow API. For the current release (`npm install affixio`) and its security changes, read the README and [2.0.0.md](2.0.0.md); where this guide and those disagree, the newer documents win.

## Delivered Surface

| Area | Implemented | Boundary |
| --- | --- | --- |
| Daily budgets | Atomic reserve, start, commit, release and reconciliation | Single host or an application-supplied transactional store |
| Decisions | Multiple sources, all/any rules, freshness, allow/deny/review | Business rules run in JavaScript, not a newly invented ZK circuit |
| Review | Authorized approval or denial tied to an immutable action | Your server must authenticate the reviewer |
| Workflow state | Restart recovery, scoped sessions, parent lineage, pagination | Store files are operational state, not an authentication boundary |
| Replay | Fixed-time policy evaluation against local observations | Does not execute actions, consume quota or contact sources |
| Source monitoring | Cancellable polling with content-change detection | Source adapters must supply accurate timestamps and restrict URLs |
| Evidence | Portable manifest, ML-DSA signing, verification and HTML report | Does not automatically verify the contents of every attached proof |
| Browser | Trusted-key ML-DSA verification and a DOM-safe summary | Verification only; no API key, HMAC secret or private signing key |
| MCP | Permission-filtered tool discovery and invocation checks | Bind it to your MCP server and authenticated request context |
| Web middleware | Express and Fastify authorization gates | Use WorkflowSession for transactional side effects |
| x402 | HTTP v2 challenge, selection, signing hook and settlement check | GET only; requires your signer, authorization and settlement verifier |
| AP2 | Normalized verified-mandate binding and replay rejection | Requires a real AP2 signed-mandate verifier; not AP2 certification |
| A2A | Task-bound evidence handover as a data part | Not a replacement A2A client/server or delegation credential |
| Python | Standard-library client using existing Node SDK API paths | No Python proving engine and no automatic retries for writes |
| Telemetry | Optional OpenTelemetry-compatible tracer/meter hooks | No exporter dependency; no inputs, keys or source values in attributes |

## Upgrading Daily Limits

In 1.4.1, `maxPerDay` was stored but not enforced cumulatively. In 2.0.0-beta.1, a capped policy denies with `daily_budget_required` unless an available budget is supplied to the pure decision function. `verifyAgentSpend` requires a BudgetLedger, a budget account and a stable request ID when a daily cap is active. It reserves before issuing an allowed proof. The reservation must then be started and committed, or released if no action began.

This intentionally changes previously permissive behavior. A local JSON file should be owned by the service account and stored outside a public web directory. Evaluate policy on your trusted service; do not accept a claimed allow decision or replacement policy from an untrusted agent request. Do not let agents choose their scope, allowance or review identity. Do not use one file per worker for a shared allowance.

`BudgetLedger.start()` must happen immediately before sending a payment. `commit()` records confirmed spend. `release()` only accepts an unstarted hold. A started payment whose outcome is uncertain needs `reconcile()` with a provider evidence reference. Only trusted server code may call reconciliation. For automatic lifecycle coordination, use WorkflowSession instead of manually sequencing ledger methods.

Duplicate legacy `verifyAgentSpend` request IDs do not issue another allowed result. Use the existing action status, not a new payment attempt. Re-evaluate under a new request ID only after the original outcome is known. No SDK can guarantee exactly-once execution by an external system: pass the supplied idempotency key to providers that support it and reconcile crashes with the provider.

Amounts use ISO-style currency decimal precision, including JPY and KWD. Fractional minor units are rejected, not rounded. x402 token amounts remain atomic-unit decimal strings and do not pass through the fiat money helper. Budget days are UTC. An uncertain execution remains reserved across midnight; it does not become free allowance the next morning.

## Decisions, Reviews and Freshness

DecisionPipeline collects explicitly registered source functions. Each receives an AbortSignal and must respect it to stop underlying I/O. A timeout returns review even if a badly behaved adapter continues its own background work. Source functions must be read-only.

Supported operators are `eq`, `gte`, `lte`, `includes` and `truthy` (strict boolean true). An unavailable, invalid or stale source requires review, including under `any` policies. `requireReview: true` routes otherwise allowed decisions to a human. Missing or expired evidence cannot be approved after expiry; collect fresh evidence and propose a new action.

The decision result stores fingerprints and check outcomes, not source values. `collect()` explicitly returns the observations for local replay. WorkflowSession persists the intent and policy you pass in. Keep raw customer records out of those objects; use references. Hashes of predictable values are not anonymization.

`dataCheckSource(adapter, queryFor)` adapts an existing SDK data-check source into a pipeline source. It reads the adapter's boolean `pass` result and never copies the returned raw fields into the decision. Its timestamp is the lookup completion time, not an assertion that the underlying database record was recently updated. If source-record freshness matters, use a custom source that supplies the record's actual timestamp.

Decisions bind the exact input digest as well as the policy digest. WorkflowSession requires the action intent to match that input. Include all relevant agent, recipient, action, amount and resource fields before evaluation. A standalone `evaluatePolicy()` call without an explicit `input` can be used for simulation, but not to authorize a workflow action.

`pipeline.prove()` returns `{ result, proof, binding }`. The binding contains the policy, input digest and decision digest, and is passed as the policy to the existing SDK HMAC proof path. Its hash is committed inside the ML-DSA-signed envelope. Keep the binding with the proof. Verify the envelope against an independently trusted public key, compare `canonicalPolicyHash(binding)` with `proof.envelope.payload.policy_hash`, and compare its input and decision digests with the exact input and result you expect. This composite hash differs from `result.policyDigest`, which hashes only the base policy. The extra `meta` fields are convenience data, not signed evidence.

Review produces no binary proof. This records a signed local decision; it does not prove that JavaScript evaluated correctly inside a ZK circuit. Existing UltraHonk APIs and circuits remain available separately. No new circuits have been claimed or added.

## Workflow Lifecycle

1. Collect current source evidence and evaluate a versioned policy.
2. Propose an action with a unique ID, stable intent and scope.
3. If review is required, authenticate the human on your server and authorize the review callback.
4. Execute through WorkflowSession. Budget reservation and execution state are committed in one transaction before the callback runs.
5. Confirm success and commit spend. A thrown error or crash leaves execution uncertain and cannot trigger an automatic second attempt.
6. Reconcile uncertain execution against provider evidence with a separately authorized operator.

Session scope and parent lineage are local application concepts. They do not enforce a global multi-agent policy unless you implement the relevant sequence checks as sources/policies. A handover receipt binds the sender, recipient, task, action and lineage head. Sign its evidence bundle and validate that trust separately before treating it as authenticated evidence. Receiving a receipt does not grant authority to spend or invoke tools.

FileStore uses synchronous exclusive-file locking, atomic rename and fsync. It targets small, single-host workloads on a local filesystem. A process killed while holding a lock may leave the lock file behind; inspect the recorded PID and confirm that no writer remains before removing it. Automatic stale-lock stealing is intentionally absent. For high throughput, multiple hosts or an untrusted shared filesystem, supply a transactional store with appropriate isolation instead. Protect and back up the store; hash chains alone cannot stop an attacker rewriting the whole file.

## Integration Contracts

Express and Fastify hooks evaluate the authenticated request. They return 403 for denial and 409 for review. They do not execute a transaction for you.

MCP `list()` filters definitions per request; `call()` repeats discovery and authorization checks before reaching the configured executor. Register these with your own MCP server's handlers. `createMcpConnection()` produces a connection descriptor and required environment variable names. It neither launches an arbitrary process nor silently injects a key. The server-only MCP helper missing from the 1.4.1 npm tarball is now included with its CLI routing. `affixio mcp print` prints configuration without writing it; `affixio mcp install --dry-run` previews changes. Explicit installation updates known client configuration files. HTTPS URL validation and exact AffixIO hostname matching prevent credentials in URLs and accidental lookalike-server matches.

For n8n, use a self-hosted Code node with the package allowed in the runner, or call your own authenticated workflow service from HTTP Request nodes. Keep the same store and server-owned scope across runs. Run evaluate/propose before the side-effect node, and confirm/reconcile afterward. `examples/mcp-workflow.mjs` shows the same callback boundary. This package does not claim to ship a registered n8n community node.

x402 uses `PAYMENT-REQUIRED`, `PAYMENT-SIGNATURE` and `PAYMENT-RESPONSE`. It rejects cross-origin resource claims and redirects. The authorization callback must validate the payee, asset, network, atomic amount, timeout and payer consent, and reserve funds before signing. The signer must bind the exact selected requirement. A settlement response is not trusted unless your verifier approves it. Missing or unverifiable settlement can still mean the payment happened; reconcile before retrying. Wrap the operation in a durable workflow. Only GET is supported, to avoid blindly replaying a side-effecting HTTP request.

The AP2 adapter calls a verifier you supply, then checks normalized principal, agent, merchant, currency, exact minor-unit amount, checkout digest and expiry. It consumes the mandate ID once under a transaction before returning authorization. This is an integration boundary, not a JOSE implementation or an assertion of AP2 end-to-end conformance. Your verifier must check the real signature, trust chain, audience, mandate type and protocol bindings. A failed execution after consumption requires reconciliation, not reusing the mandate.

## Evidence and Trust

Evidence levels are explicit:

| Level | What it establishes |
| --- | --- |
| Fingerprint consistency | The content matches the manifest; an attacker can still create a new unsigned manifest |
| Trusted ML-DSA signature | The pinned signer signed the exact manifest or payload |
| HMAC decision proof | A local shared-secret proof and signed decision, not a zero-knowledge execution proof |
| Verified UltraHonk proof | The circuit relation checked by the existing ZK verifier, with its circuit and key assumptions |
| Verified remote attestation | An attestation checked against the remote authority's trusted key and expected statement |
| Merkle inclusion | Inclusion under a separately trusted tree head; not independent source truth |

Never trust a public key merely because it arrived inside the same bundle. Obtain it independently and pass it through `trustedPublicKeys`. The browser verifier checks ML-DSA and payload binding without an API key. It does not check HMAC, UltraHonk, remote attestations or legal compliance. Attached proof files are opaque evidence until their specific verifier checks them. The HTML report uses escaped text and does not execute artifact content.

`affixio-evidence verify` returns exit status 0 only when manifest integrity and a trusted signature both pass. An unsigned but internally consistent bundle returns status 1. `--report` refuses to overwrite an existing file.

## Python

`python/affixio_client.py` has no third-party dependencies. It maps to the routes already in `dist/client.js`: auth check/pulse, circuits, circuit verify, Merkle root/audit/verify, aggregate verify and attest. Keys stay in headers, redirects are refused and writes are not automatically retried. Remote calls require valid API access and applicable entitlements. This is not a Python-native ZK prover. Use the Node SDK to produce proofs, then exchange JSON proof records with Python.

## Validation And Release Boundaries

The suite covers store transactions, cross-process contention, budget expiry, restart recovery, review authorization, stale sources, lineage, real ML-DSA signatures, tampering, package exports, TypeScript consumers and Python request contracts. Payment tests use fixtures, not live charges. Optional telemetry tests use injected tracer/meter implementations.

Before publishing, run the full suite, package checks and an install smoke test. Live API, licence, UltraHonk execution, Stripe and payment-provider conformance require their real integration environments and are not certified by these offline tests. No service or price was changed by this build.
