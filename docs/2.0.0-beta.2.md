# AffixIO SDK 2.0.0-beta.2: Security Notes

This review build fixes two issues found while testing AffixIO with Zenoh. Both are **breaking security changes** for code that verified envelopes without pinning a key.

## 1. ML-DSA signer pinning (high)

**Problem (1.x, 2.0.0-beta.1):** `verifyLocalPayload` / `verifyProofEnvelope`, and everything built on them, read `mldsa_public_key_b64` from the envelope, checked that `key_id = sha256(key)[0:16]` matched, and verified the signature with that same key. An attacker could generate any ML-DSA-65 key pair, sign their own payload, and it verified.

**Fix:** verification takes trusted keys and checks the signature with the **trusted** key bytes. Envelopes whose `key_id` is not pinned, or whose embedded key differs from the pinned key, are rejected (`untrusted_signer`). With no trust configured, verification **fails closed** with `AffixTrustError("no_trusted_keys")`. It never falls back to the embedded key.

### Two kinds of signer

| Artifact | Signed by | Pin with |
| --- | --- | --- |
| `prove()` envelopes, evidence bundles, spend journal | The host's **own local** ML-DSA-65 key (`signingKeys`) | Host config. `AffixSDK` pins its own key by default. Other hosts pin it via `trustedSigningKeys` / `trustedKeys` (export it with `sdk.exportLocalPublicKey()`). |
| AffixIO API attestations (`/api/attest`, server proofs) | The **AffixIO server** key | The published key set `GET https://api.affix-io.com/v1/keys` (alias `/.well-known/affixio-keys.json`). |

### Trusted key formats (`trustedKeys`)

- A base64 (or hex) ML-DSA-65 public key, or raw bytes
- `{ key_id, public_key_b64 }`, or an array of such objects or strings
- `{ "<key_id>": "<public_key_b64>" }`
- A key set document `{ schema: "affix.keys.v1", keys: [{ key_id, algorithm: "ML-DSA-65", public_key_b64, status, not_before, not_after }] }`. Signatures whose `signed_at` falls outside a key's window are rejected, and `revoked` keys are ignored.

### APIs

```js
import { verifyLocalAttestation, verifyProofEnvelope, AffixTrustError } from "affixio";
verifyLocalAttestation(payload, attestation, { trustedKeys, hmacSecret?, requireHmac?, insecureTrustEmbeddedKey? });
// -> { valid, reason, key_id, hmacVerified, signatureVerified }
verifyProofEnvelope(envelope, hmacSecret, { trustedKeys });    // boolean
verifyProofEnvelope(envelope, { trustedKeys });                // ML-DSA only (devices)

const sdk = new AffixSDK({ apiKey, trustedSigningKeys: [peerKey], role: "server" });
await sdk.verifyLocal(circuit, proofHex, { envelope });        // own key + peers pinned
sdk.trustedKeys();                                              // public keys in use

import { fetchAffixioKeys, verifyAffixioAttestation } from "affixio";
const keys = await fetchAffixioKeys();                          // fetched once, cached 1h
await verifyAffixioAttestation(payload, attestation, { trustedKeys: keys });

import { verifyArtifactOffline, verifySignedRoot } from "affixio/offline"; // same module as affixio/sth
verifyArtifactOffline({ proof, attestation, trustedKeys });
verifySignedRoot(sth, pinnedKeyOrKeySet);

import { verifyEvidenceBundle } from "affixio/browser";
await verifyEvidenceBundle(bundle, { trustedPublicKeys: [b64] }); // or { trustedKeys: keySet }
```

CLI:

```
affixio-evidence verify bundle.json --trusted-key key.txt|key.json [--trusted-keyset keys.json]
affix-sdk-ext verify-offline --attestation envelope.json --trusted-key signer.pub.json [--hmac-secret s]
```

Both refuse to verify a signed artifact when no key is pinned.

`insecureTrustEmbeddedKey: true` restores the old behaviour **for tests only** and emits the `AFFIXIO_INSECURE_TRUST_EMBEDDED_KEY` warning.

### Offline devices

Fetch `https://api.affix-io.com/v1/keys` once while online, or copy a gateway's `exportLocalPublicKey()` output. Store it with the device image and pass it as `trustedKeys`. When a key is rotated, the old one stays in the set as `retired`, with `not_after` set.

## 2. HMAC (`affix-light-v1`) on devices (medium)

HMAC verification needs the shared secret, so any party that can verify an HMAC proof can also forge one. HMAC mode is for **servers and trusted parties only**.

- `role: "server"` (default) or `"trusted-party"`: HMAC proofs verify as before. A one-time `AFFIXIO_HMAC_TRUSTED_PARTY_ONLY` warning is emitted (silence it with `silenceHmacWarning: true`).
- `role: "device" | "edge" | "offline-verifier"`: `verifyLocal` on an HMAC proof throws `AffixHmacRoleError` (`code: "hmac_verify_refused_for_role"`). Envelope checks on these roles are ML-DSA only. Devices do not need, and should not hold, the HMAC secret.
- For devices, verify the ML-DSA-65 envelope against pinned keys, or use UltraHonk proofs.

## 3. Replay guard

```js
import { createReplayGuard, MemoryReplayStore } from "affixio"; // also affixio/workflows
const guard = createReplayGuard({ windowMs: 5 * 60_000, clockSkewMs: 30_000, store: new MemoryReplayStore() });
const r = await guard.check({ id: cmd.cmd_id, issuedAtMs: cmd.issued_at_ms }); // { ok, reason }
```

Reasons: `fresh`, `replay`, `expired`, `timestamp_in_future`, `missing_id`, `missing_timestamp`. For several verifier processes, provide a shared store implementing `putIfAbsent(id, expiresAtMs, nowMs)` atomically (for example Redis `SET NX PX`).

## Not changed

- Proof, envelope and attestation formats.
- Server-side HMAC proving and verification.
- `fetchSignedRoot` still fetches over TLS. For strict pinning, verify the returned STH yourself with `verifySignedRoot(sth, pinnedKeySet)`.
